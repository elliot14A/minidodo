# AI_USAGE.md

An honest account of how I used AI on this assignment.

## Tools and how I used them

I used two setups, split by the job.

- **Coding: Antigravity with Gemini 3.7 Flash.** For writing the actual code I used the
  Antigravity agent running Gemini 3.7 Flash. I like how fast and straightforward it is: it
  produces conforming code quickly without a lot of ceremony, which is exactly what I want once the
  design is settled.
- **Brainstorming, research, and code review: OpenCode with Claude Opus 4.8.** For the thinking
  work (design, researching how real payment systems handle failure, and reviewing the generated
  code) I used OpenCode running Claude Opus 4.8. It is stronger at sustained reasoning and at
  defending or dropping a suggestion under pushback.

Both were driven through GSD (Git. Ship. Done.), a plan-driven agentic workflow. GSD is not
autocomplete. It forces a project through explicit stages before any code is written: an initial
questioning and research pass, then a `REQUIREMENTS.md` and a phased `ROADMAP.md`, then per-phase
planning (`PLAN.md`), then execution with state tracking (`STATE.md`) and atomic commits, and a
summary per phase (`SUMMARY.md`). I kept all of this in the repo on purpose. `.planning/` holds the
requirements, roadmap, and the per-phase plans and summaries (phases 01 through 07), and `.agents/`
holds the GSD workflows and my own opinionated skills. Reading those two directories shows exactly
how I used AI, phase by phase, rather than asking you to take my word for it.

The workflow, roughly: `gsd-new-project` to turn the assignment into requirements and a roadmap,
`gsd-plan-phase N` to produce a detailed plan for each phase, `gsd-execute-phase N` to build it,
and a verification pass before moving on. Each phase (workspace and errors, auth, customers,
invoices, mock PSP, payments and worker, webhooks) was planned, built, and committed as a unit.

Most of the code in this repo was generated by AI (Gemini 3.7 Flash in Antigravity), but not
blindly. I steered it with a set of opinionated Rust skills I maintain and included under
`.agents/skills/` (`rust-standards` and `rust-code-review`). These encode the conventions I already
work in: a Cargo workspace split into `core` / `infra` / `server` / `worker` / `psp`, snafu-based
error handling that all maps to one `MinidodoError`, lowercase SQL keywords, a 3-tier route layout,
and pure async functions over trait-object ceremony. Gemini generated code that conformed to those
skills, and I ran it back through Claude Opus 4.8 in OpenCode against the same `rust-code-review`
checklist. So the efficiency came from a fast model doing the typing inside guardrails I own, with a
stronger model reviewing, not from me accepting whatever came out.

## Brainstorming and research (how the design was found)

A large part of the early work was brainstorming with Claude Opus 4.8 in OpenCode, and I
deliberately told it to research rather than reason from first principles. The hard questions were: how do you guarantee no double
charge under concurrency, what happens on a PSP timeout, and how does a payment recover if the
service crashes mid-charge. I asked it to go study how real payment processors like Stripe and
Adyen actually handle these failure points and to bring back sourced findings instead of a
plausible-sounding invention.

That research is where the core of the design came from. The sources I leaned on were Stripe's
idempotency docs and engineering blog, Stripe's PaymentIntent lifecycle and webhook docs, Adyen's
guidance on idempotency and payment result handling, and Brandur Leach's write-ups on idempotency
keys as recovery records and the transactionally-staged job drain. From those I took the specific
mechanisms in this design: the idempotency key row as a recovery record with a `recovery_point`,
atomic phases with the foreign PSP call sitting between committed transactions, a completer worker
that resumes a payment stuck after a crash, a derived idempotency key sent downstream to the PSP so
a retry cannot double charge, and webhooks as the channel that delivers the eventual result. When
the model's first research pass was too vague, I sent it back for primary sources and to label each
finding against one.

## Three decisions I made myself

The design came out of disagreement with Claude during the brainstorming phase, not agreement. The
main points where I overrode it:

1. **No row locks across the PSP call.** The model offered `SELECT FOR UPDATE` as the simple
   concurrency answer. I pushed back: holding a row lock across a 30s PSP call blocks the second
   payer on the slowest possible thing. I chose a status-conditional `UPDATE` claim instead, where
   the loser gets a `409` immediately and no lock is held across the network call.

2. **Always return 202.** The model proposed a hybrid: return 200 inline when the PSP is fast, 202
   when slow. I chose 202 for every payment. One consistent contract is simpler to build, test, and
   explain, and it is honest that a PSP call is never truly synchronous. The result always arrives
   by webhook or by `GET`.

3. **Pure Postgres over a message broker.** The model initially suggested adding RabbitMQ or Redis
   for async payment completion and webhook retries. I chose to keep all async work in Postgres
   via `pg_notify` for latency and domain table recovery sweeps for durability. This eliminates
   moving parts and makes the system trivial to run in Docker Compose with only Postgres.

I also pressed the model repeatedly on the crash-recovery questions (server crashes
mid-`processing`, PSP charged but we crashed before saving it, client loses the idempotency key).
Its first answers were incomplete or left the invoice stuck. I kept asking until the explanation was
concrete, which is how the completer plus derived-key design got nailed down.

## One thing the model got wrong

During design, Claude kept describing `tok_timeout` as a payment that eventually fails, and at one
point built a recovery story on "the timeout means the charge failed." That is wrong. The spec says `tok_timeout`
sleeps 30 seconds and then returns success. It is a slow success, not a failure.

This matters. If you treat the client-side timeout as a failure and reopen the invoice, you reject a
payment the PSP actually accepted, and you answer the "how does the caller find out the eventual
result" question incorrectly, because there is a real successful result to deliver. The corrected
design leaves the invoice in `processing`, lets the worker wait for the real 30s success, and then
fires `invoice.paid`. `tok_network_error` is the only genuinely failed path. I confirmed the
correction by re-reading the mock PSP token table in the assignment directly instead of trusting the
model's paraphrase.
