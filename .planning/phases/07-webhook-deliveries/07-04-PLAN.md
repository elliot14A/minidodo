# Plan 07-04: Worker Webhook Listener, Inline Retry Deliverer, and Mock Sink

## Goal
Add signed webhook delivery to the `minidodo-worker` process, driven by `LISTEN webhooks`
with a `for update skip locked` claim, mirroring the payment NOTIFY path. Retries happen
inline in the deliverer with exponential backoff sleeps. There is no sweep and no crash
recovery: a lost notification or a worker crash mid delivery is not recovered (accepted cut,
DESIGN.md section 6). Add the verifying `POST /webhooks/sink` endpoint to `minidodo-psp`.
No transaction is held across the outbound HTTP call.

## Proposed Changes

### 1. `minidodo-worker/src/webhook_deliverer.rs`
- `deliver(pool, delivery, endpoint) -> Result<()>` shared delivery logic with an inline
  retry loop:
  - Serialize the `WebhookEventPayload` to bytes once.
  - Loop for `attempt` in `1..=WEBHOOK_MAX_ATTEMPTS`:
    - `timestamp = current unix seconds`; `signature = sign_payload(endpoint.signing_secret,
      timestamp, &body)`.
    - POST to `endpoint.url` with headers `content-type: application/json`,
      `X-Webhook-Signature: sha256=<hex>`, `X-Webhook-Timestamp: <unix>`, using a `reqwest`
      client with a short timeout (for example 10s).
    - On `2xx`: `actions::webhooks::mark_delivered(pool, delivery.id, attempt)` and return.
    - On non-2xx or transport error: if `attempt < WEBHOOK_MAX_ATTEMPTS`,
      `tokio::time::sleep(backoff_secs(attempt))` and continue; else break out of the loop.
  - After the loop exhausts: `actions::webhooks::mark_failed(pool, delivery.id,
    WEBHOOK_MAX_ATTEMPTS, error)` and log with `WebhookErrorCode::DELIVERY_FAILED`.
  - Holds no DB transaction across the HTTP call or the sleeps.

### 2. `minidodo-worker/src/webhook_listener.rs`
- `LISTEN webhooks` on a dedicated sqlx connection. On each notification (payload =
  delivery id), `actions::webhooks::claim`; if claimed, spawn `webhook_deliverer::deliver`
  as its own task so the inline backoff sleeps do not block draining further notifications.
  If `claim` returns `None` (already handled or held), do nothing. This is the only delivery
  driver; there is no sweep.

### 3. `minidodo-worker/src/completer.rs`
- After `settle_success` / `settle_failure` return the staged delivery ids, fire
  `actions::webhooks::notify_webhook(pool, delivery_id)` for each. This is the enqueue signal.
  There is no backstop; if the notify is lost the delivery is not retried.

### 4. `minidodo-worker/src/serve.rs` and `lib.rs`
- Spawn the webhook listener alongside the existing payment listener and payment sweep in the
  same `tokio::select` supervision. Declare the new modules in `lib.rs`. No webhook sweep task
  is added.

### 5. `minidodo-psp` mock sink
- `state.rs`: add the shared `signing_secret` to the PSP app state, sourced from config.
- `http/routes/v1/webhooks/sink.rs`: `POST /webhooks/sink`. Read `X-Webhook-Signature` and
  `X-Webhook-Timestamp` headers and the raw body. Call
  `minidodo_core::models::webhook::verify_signature(secret, timestamp, &body, signature)`.
  Return `200 OK` on a match (log `webhook received and verified`), `401` on a mismatch or
  missing headers. It does not store or process the payload further.
- `routes.rs` / `mod.rs` / `v1/mod.rs`: mount the route under the PSP router.

### 6. `minidodo-core` config
- `MockPspConfig`: add `webhook_signing_secret` (default `whsec_test_secret_12345`, matching
  the seeded endpoint in plan 07-01) via `MINIDODO_PSP_WEBHOOK_SIGNING_SECRET`.
- The worker needs no new config; it reads the endpoint secret from the joined `webhooks` row
  returned by `claim`.

### 7. `docker-compose.yaml`
- No new service. The `worker` already reaches the `psp` service, and the seeded endpoint url
  `http://psp:3000/webhooks/sink` resolves inside the compose network. Confirm the `psp`
  service passes `MINIDODO_PSP_WEBHOOK_SIGNING_SECRET` or relies on the default that matches
  the seed.

## Verification
- `cargo check --all-targets` and `cargo clippy --all-targets -- -D warnings` pass clean.
- With the full stack up, create and finalize an invoice, then `POST /pay` with `tok_success`.
  Within ~1 to 2s the `webhook_deliveries` row for `invoice.paid` shows `status = 'delivered'`,
  `attempts = 1`, and the `psp` logs show `received and verified`.
- `POST /pay` with `tok_card_declined` produces an `invoice.payment_failed` delivery that
  reaches `delivered`.
- Retry and give up: temporarily make the sink return 500 (or point the seed at an unroutable
  url), settle an invoice, and confirm the deliverer retries with growing backoff sleeps and
  the row lands in `status = 'failed'` with `attempts = WEBHOOK_MAX_ATTEMPTS`, without
  blocking payment settlement or the pay endpoint.
- Fails when: delivery blocks the pay endpoint or the settle path, a delivery is sent
  unsigned, the sink returns 200 on a bad signature, a delivered row is re-delivered, or a
  webhook sweep exists.
