# Plan 07-03: Webhook Infra Actions and Transactional Outbox Staging

## Goal
Implement the webhook database actions in `minidodo-infra`, one action per file, and wire the
outbox staging into the two Phase 2 settle transactions so a settled payment always enqueues
its delivery atomically. No lock or open transaction is held across the outbound HTTP call:
the worker claims with `for update skip locked`, releases, delivers, then updates with a
status conditional write. There is no sweep and no re-drivable dead letter queue. Every query
is tenant-scoped by `business_id`.

## Proposed Changes

### 1. `actions/webhooks/stage.rs`
- `stage_deliveries(tx, business_id, event_type, payload) -> Vec<Uuid>` running inside a
  caller supplied transaction. It selects every `active` endpoint for the business
  (`select id from webhooks where business_id = $1 and active = true`) and for each inserts a
  `webhook_deliveries` row (`status 'pending'`, `attempts 0`). Returns the inserted delivery
  ids so the caller can notify after commit. Takes `&mut PgConnection` / the transaction
  handle, not the pool, so it joins the settle tx.

### 2. `actions/webhooks/notify.rs`
- `notify_webhook(pool, delivery_id)` running `select pg_notify('webhooks', $1)` with the
  delivery id as text. Mirrors the payments `notify.rs`.

### 3. `actions/webhooks/claim.rs`
- `claim(pool, delivery_id) -> Option<(WebhookDelivery, WebhookEndpoint)>` for the NOTIFY
  path. Uses a CTE with `for update skip locked` to lock the single delivery row if it is
  still `pending` and return it joined to its endpoint (`webhooks.url`,
  `webhooks.signing_secret`). Returns `None` if another worker holds it or it is no longer
  pending. This is the only claim path; there is no sweep counterpart.

### 4. `actions/webhooks/mark_delivered.rs`
- `mark_delivered(pool, delivery_id, attempts) -> bool` setting `status = 'delivered'`,
  `attempts = $attempts`, `last_attempt_at = now()` where the row is still `pending`. Status
  conditional so a duplicate delivery cannot flip a terminal row. `attempts` is the count the
  inline loop actually used.

### 5. `actions/webhooks/mark_failed.rs`
- `mark_failed(pool, delivery_id, attempts, error) -> bool` setting `status = 'failed'`,
  `attempts = $attempts`, `last_error = $error`, `last_attempt_at = now()` where the row is
  still `pending`. Called once after the inline retry loop exhausts all attempts. `failed` is
  observability only; nothing re-drives it.

### 6. `actions/webhooks/mod.rs` and `actions/mod.rs`
- Declare the five action modules and re-export their functions. Add `pub mod webhooks;` to
  `actions/mod.rs`.

### 7. Wire staging into the settle transactions
- `payments/settle_success.rs`: after the `invoices` update to `paid` and before
  `tx.commit()`, call `crate::postgres::actions::webhooks::stage::stage_deliveries(&mut *tx,
  business_id, WebhookEventType::InvoicePaid, payload)` with a payload built from the attempt
  and invoice (invoice_id, attempt_id, psp_ref). Change the return so the caller receives the
  staged delivery ids (for example return `Ok(Some(delivery_ids))` on the settle path, or add
  an out struct). The existing `Ok(false)` no-op path when the attempt is not `pending`
  stages nothing.
- `payments/settle_failure.rs`: same, staging `WebhookEventType::InvoicePaymentFailed` with
  the error_code in the payload.
- Both remain a single transaction. If the settle rolls back, no delivery is staged.

## Verification
- `cargo check --all-targets` and `cargo clippy --all-targets -- -D warnings` pass clean.
- Manual SQL sanity after a live settle: `select event_type, status, attempts from
  webhook_deliveries order by created_at desc limit 5` shows one `pending` row per active
  endpoint immediately after an invoice settles, inside the same transaction as the state
  change (no orphan state change without a delivery, no delivery without a state change).
- Fails when: staging runs in its own transaction rather than the settle tx, `claim` does not
  use `for update skip locked`, any action holds a row lock across an await that is not a DB
  call, `unwrap`/`expect` appears, or clippy warns.
