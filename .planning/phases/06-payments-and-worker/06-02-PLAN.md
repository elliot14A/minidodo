# Plan 06-02: Payment Domain Models and Database Actions

## Goal
Implement payment domain models in `minidodo-core` and the granular actions in `minidodo-infra` that back the `/pay` endpoint and the worker. All money is `i64` cents. No lock or open transaction is held across a PSP call: Phase 1 (claim) and Phase 2 (settle) are separate committed transactions. Every query is tenant-scoped by `business_id`.

## Proposed Changes

### 1. `minidodo-core` Domain Models & Error Codes
- `PaymentStatus` enum: `Pending`, `Succeeded`, `Failed` (`#[derive(Debug, Clone, Copy, PartialEq, Eq, Serialize, Deserialize, sqlx::Type, ToSchema)]`, `#[sqlx(type_name = "payment_status", rename_all = "lowercase")]`), matching the `InvoiceState` pattern in `invoice.rs`.
- `RecoveryPoint` enum: `ChargePending`, `Finished` (same derive pattern, `type_name = "recovery_point"`).
- `PaymentAttempt` struct deriving `sqlx::FromRow`, `Serialize`, `Deserialize`, `ToSchema`.
- `IdempotencyRecord` struct deriving `sqlx::FromRow`.
- Add `PaymentErrorCode` usages if missing: reuse existing `PaymentErrorCode::INVOICE_NOT_PAYABLE`; add `PaymentErrorCode::IDEMPOTENCY_KEY_CONFLICT` (`"PAYMENT_IDEMPOTENCY_KEY_CONFLICT"`) for the same-key-different-payload case.
- Helper to compute `payload_hash`: SHA-256 hex of the canonicalized request body (reuse the `sha2` crate already used for API keys).

### 2. `minidodo-infra` Database Actions (`actions/payments/`)
- `idempotency.rs`:
  - `lookup(pool, business_id, key) -> Option<IdempotencyRecord>`.
  - Caller compares `payload_hash`: on match with a finished record, replay stored `response_code` + `response_body`; on mismatch, return `422` (`IDEMPOTENCY_KEY_CONFLICT`).
- `create_attempt.rs`: `insert_attempt(tx, invoice_id, business_id, idempotency_key, payload_hash) -> PaymentAttempt` (status `pending`). Runs inside the Phase 1 transaction.
- `claim_invoice.rs`: `claim(tx, business_id, invoice_id) -> u64` running the status-conditional claim `update invoices set state='processing' where id=$1 and business_id=$2 and state='open'`. Returns rows affected. 0 rows means the invoice was not `open` (loser of a race, or already paid/void), caller returns `409` (`INVOICE_NOT_PAYABLE`).
- `create_attempt.rs` / `idempotency.rs`: upsert the `idempotency_keys` row at `recovery_point='charge_pending'`, `locked_at=now()`, storing `payload_hash`. All of Phase 1 commits together.
- `settle.rs`: `settle_success(pool, attempt_id, psp_ref, response)` and `settle_failure(pool, attempt_id, psp_error_code, response)`, each a single Phase 2 transaction:
  - success: `update invoices set state='paid' where id=$1 and state='processing'`; `update payment_attempts set status='succeeded', psp_ref=$..`; `update idempotency_keys set recovery_point='finished', last_run_at=now(), response_code=$.., response_body=$..`.
  - definitive failure: `update invoices set state='open' where id=$1 and state='processing'`; attempt `failed`; idempotency `finished` with stored response.
- `recover.rs`:
  - `find_stale(pool) -> Vec<..>` running `select ... from idempotency_keys where recovery_point <> 'finished' and locked_at < now() - interval '60 seconds'` joined to the attempt.
  - `reclaim(pool, business_id, key) -> bool` setting `locked_at = now()` conditionally on the row still being stale, so two sweeps do not both grab it.
