# Plan 06-03: Pay Endpoint and pg_notify

## Goal
Implement `POST /v1/invoices/{id}/pay`. It performs the Phase 1 committed transaction, fires `pg_notify('payments', <attempt_id>)`, and returns `202 Accepted`. The endpoint never calls the PSP. It is idempotent via the `Idempotency-Key` header and handles failure modes (a), (d), (e) from DESIGN.md §3.

## Proposed Changes

### 1. `minidodo-infra/src/postgres/actions/payments/notify.rs`
- `notify_payment(pool, attempt_id)` running `select pg_notify('payments', $1)` with the attempt id as text.

### 2. `minidodo-server/src/http/routes/v1/invoices/pay.rs`
- Request: reads `Idempotency-Key` header (required; missing -> `400`). Body carries `{"card_token": "..."}`, validated with `ValidatedJson`.
- Compute `payload_hash` from the canonical request (card_token + invoice id + business id).
- Idempotency check first (`actions::payments::idempotency::lookup`):
  - existing finished record, same `payload_hash` -> replay stored response (same status code + body).
  - existing record, different `payload_hash` -> `422` (`PAYMENT_IDEMPOTENCY_KEY_CONFLICT`, "idempotency key reused with a different payload").
- Otherwise Phase 1 transaction (`pool.begin()`):
  - insert `payment_attempts` row (`pending`).
  - claim invoice `open -> processing`; if 0 rows -> mark attempt `failed`, return `409` (`INVOICE_NOT_PAYABLE`, message names the current state). Covers (a) race loser and (e) already-paid.
  - upsert `idempotency_keys` at `recovery_point='charge_pending'`, `locked_at=now()`, storing `payload_hash`.
  - commit.
- After commit: `actions::payments::notify::notify_payment(pool, attempt_id)`.
- Return `202 Accepted` with a small body (`{"attempt_id": ..., "invoice_id": ..., "status": "processing"}`).
- No lock or transaction is held across any network call; the PSP is not called here.

### 3. Routes and OpenAPI
- `routes.rs`: add `.route("/{id}/pay", post(super::pay::pay))`.
- `mod.rs`: register `pay::pay` and its request schema in `InvoicesApiDoc`.

## Verification
- `cargo build` and `cargo clippy --all-targets -- -D warnings` pass clean.
- Create + finalize an invoice, then:
  - `curl -X POST /v1/invoices/{id}/pay -H 'Idempotency-Key: k1' -d '{"card_token":"tok_success"}'` -> `202`, invoice becomes `processing`.
  - Same call again with `k1` and same body -> same response (replay), no new attempt row.
  - Same key `k1` with a different `card_token` -> `422`.
  - `POST /pay` on a `draft` or `paid` invoice -> `409` naming the current state.
- Fails when: any of the above returns a different status, a second attempt row is created on replay, or the endpoint blocks (no PSP call should occur here).
