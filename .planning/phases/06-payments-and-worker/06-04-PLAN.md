# Plan 06-04: Worker Crate, PSP Client, Completer, and CLI Subcommand

## Goal
Add the `minidodo-worker` crate mirroring the `minidodo-psp` crate layout. One process runs both the LISTEN/NOTIFY listener (fast path) and the recovery sweep (crash backstop). Both call the mock PSP over HTTP with the derived key `invsvc-<attempt_id>` and settle the payment. Wire a `worker` CLI subcommand alongside `server`, `migrate`, and `psp`.

## Proposed Changes

### 1. `minidodo-worker` crate (mirror `minidodo-psp` structure)
- `Cargo.toml`: depends on `minidodo-core`, `minidodo-infra`, `tokio`, `reqwest`, `sqlx`, `serde`, `uuid`, `tracing`, `snafu`.
- `lib.rs`: `pub mod` declarations, `pub use serve::serve`.
- `serve.rs`: `serve(config) -> Result<()>` builds the DB pool, spawns the listener task and the sweep task, and awaits them.
- `psp_client.rs`: `charge(base_url, amount_cents, card_token, derived_key) -> PspOutcome`. POSTs `{amount_cents, card_token}` to the PSP `POST /v1/charges`, passing the derived key `invsvc-<attempt_id>`. Maps the response:
  - `200 {status:"succeeded", psp_ref}` -> success.
  - `500` or a transport/connection error (`tok_network_error`) -> definitive failure.
  - `400 {status:"failed", code}` (`tok_card_declined`, `tok_insufficient_funds`) -> definitive failure with the code.
  - A slow response (`tok_timeout`, ~30s) resolves to success when it returns; the client uses a request timeout comfortably above 30s so a slow success is not aborted.
- `completer.rs`: `complete(pool, psp_base, attempt) -> Result<()>` shared settle logic. Loads the attempt + invoice, calls `psp_client::charge` with the derived key, then calls `actions::payments::settle::settle_success` or `settle_failure`. Holds no DB transaction across the PSP call.
- `listener.rs`: `LISTEN payments` via a dedicated sqlx connection. On each notification (payload = attempt id) it runs `completer::complete`. This is the normal, low-latency path.
- `sweep.rs`: loop every `interval` (default 2s). Runs `actions::payments::recover::find_stale`, then for each row `reclaim` and `completer::complete`. Reclaim threshold is 60s, which exceeds the 30s `tok_timeout`, so a slow-but-alive charge is not reclaimed underneath itself. This is the crash backstop for a lost notification. The sweep also runs once on startup to recover anything stuck while the worker was down.

### 2. `minidodo-core` worker config (figment, mirror `psp.rs`)
- `WorkerConfig` loading `MINIDODO_WORKER_PSP_BASE_URL` (default the compose PSP url) and `MINIDODO_WORKER_SWEEP_INTERVAL_SECS` (default 2). `load_worker_config()`.

### 3. `minidodo-cli`
- `cli.rs`: add `Worker` to `MinidodoCommands`.
- `commands/worker.rs`: `run()` loading `load_worker_config()` and calling `minidodo_worker::serve`.
- `main.rs`: match arm `MinidodoCommands::Worker => worker::run().await`.

### 4. Workspace and compose
- `Cargo.toml`: add `minidodo-worker` to workspace members.
- `docker-compose.yaml`: add a `worker` service using the same image with `command: ["worker"]`, env for DB url and `MINIDODO_WORKER_PSP_BASE_URL` pointing at the `psp` service, depends_on postgres and psp.

## Verification
- `cargo build` and `cargo clippy --all-targets -- -D warnings` pass clean.
- With the full stack up (`docker compose up`), create + finalize an invoice, then `POST /pay` with `tok_success` -> invoice reaches `paid` within ~1-2s (NOTIFY path); `GET /invoices/{id}` shows `paid` and a `psp_ref` on the attempt.
- `POST /pay` with `tok_timeout` -> endpoint returns `202` immediately, invoice settles to `paid` about 30s later when the PSP responds; the endpoint never blocks.
- `POST /pay` with `tok_network_error` -> invoice returns to `open`, attempt `failed`.
- Crash backstop: stop the worker, `POST /pay` (row left at `charge_pending`), restart the worker -> the startup sweep picks up the stale row within the reclaim window and settles it.
- Fails when: an invoice stays in `processing` indefinitely after the worker is running, the endpoint blocks on `tok_timeout`, or any clippy warning appears.
